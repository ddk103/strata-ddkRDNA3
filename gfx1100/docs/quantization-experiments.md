# 量化实验记录：七次尝试与最终结论

> 全部在同一台机器、同一语料、同一参数下测得，可直接横向对比。
> 判据：**perplexity 越低越好**。原版 `UD-IQ4_XS` 是本仓库一切对比的基线。
>
> **一句话结论**：用**已量化的模型**做源，无论怎么调类型表和 imatrix，
> 都追不上用 **BF16 源**量化出来的原版。差 8.7%（K-quant 路线）。

---

## 测试方法

```bash
llama-perplexity.exe -m <模型> -f game-corpus-mixed.txt -c 512 --chunks 50 -t 8
```

- 语料：13.13 MB，Godot/Unity 代码 + agent 轨迹 + 技能文档，按 50 行分块轮转
- 上下文 512，50 个 chunk
- 同一语料既用于我们自己的 imatrix 校准，也用于 PPL 评估——**这会让结果偏向我们的模型，
  而它仍然更差**
- 硬件：RX 7900 XTX + Ryzen 7 9700X + 125.5 GiB，Windows 11 26200（详见 `test-environment.md`）

## 被证伪的三个假设

| 假设 | 实验 | 结果 |
|---|---|---|
| 「二代量化误差是主因，用 Q8 就够」 | 第 2 vs 3 组 | 只回收 1.2% → **证伪** |
| 「位宽不够」 | 第 1 vs 2 组（多 0.12 BPW） | 无变化 → **证伪** |
| 「imatrix 来源是关键」 | 第 4 vs 5 组（无 vs 官方） | 官方 imatrix 反而差 0.4% → **证伪** |
| 「位宽分配反了（down 该更高）」 | 第 6 组 | 差 8.4% → **证伪** |

## 真正的规律：i-quant 对源精度敏感，K-quant 不敏感

把实验按「源精度 × 类型族」重排，规律立刻显现：

| 类型族 | 源 | PPL 区间 |
|---|---|---|
| **i-quant**（IQ3_XXS / IQ2_S / IQ3_S） | Q8_0 | **7.24 ~ 7.36** |
| **K-quant**（Q4_K） | Q8_0 | **6.79 ~ 6.85** |
| **i-quant** | **BF16** | **6.25**（原版） |

**同一份 Q8 源，i-quant 比 K-quant 差 8%。**

### 原因在 `llama-quantize` 自己的警告里

```
--allow-requantize
allow requantizing tensors that have already been quantized
WARNING: this can severely reduce quality compared to quantizing
from 16bit or 32bit!
```

- **K-quant** 用简单的 min/max 缩放 + 分块量化，对输入的小扰动**鲁棒**
- **i-quant** 做重要性加权的**网格/码本搜索**，对输入数值敏感；从 Q8_0 反量化回来的值
  与原始 BF16 有微小差异，足以让搜索落到次优的格点分配上

原版是用 BF16 直接量化的，完全避开这个问题。

## 结论

**从已量化的模型做源，追不上原版。** 两条路：

| 路线 | 可达 PPL | 相对原版 | 成本 |
|---|---|---|---|
| K-quant + 现有 Q8 源 | **6.79** | +8.7% | 已完成（约 1 小时） |
| **i-quant + BF16 源** | 预期 ≈6.25 或更好 | 待测 | 下载 330 GB（10~16 h）+ 量化 1 h |

**要真正达到或超过原版，必须从 BF16 开始。** 这不是调参问题，是量化器对输入精度的
硬性要求。

### 如果只想比原版小、接受略差

第 4 组（Q8 源 + 无 imatrix + K-quant）是这条路的终点：**6.7897，91.96 GiB**。
比原版小 5%、慢 9%，换来的是自己完全掌控的量化流程。

## 复现步骤

```bash
# 1. 基线
llama-perplexity -m <UD-IQ4_XS shard1> -f corpus -c 512 --chunks 50 -t 8

# 2. 从 Q8 量化（K-quant，不要用 i-quant）
llama-quantize --allow-requantize \
  --output-tensor-type Q6_K --token-embedding-type IQ4_XS \
  <Q8 shard1> <out.gguf> Q4_K_M <threads>

# 3. 从 BF16 量化（i-quant，需要 BF16 源）
llama-quantize --imatrix <unsloth.imatrix> --tensor-type-file <types> \
  <BF16 shard1> <out.gguf> Q4_K_M <threads>

# 4. 打 pack：hc_* 等小张量必须是 BF16，否则 iq_pack.py 拒绝
python tools/iq_pack.py --compat-bf16 --gguf <out.gguf> --out <packdir>
```

## 踩过的坑（每一个都浪费过时间）

| 坑 | 症状 | 解法 |
|---|---|---|
| `--keep-split` + 引擎同时运行 | `did not find weights`、写盘 0 MB/s、内存见底 | 停引擎再量化。那条报错**不是致命的**，是分片搜索的正常提示 |
| robocopy `/J` 复制大模型 | **目标比源多 192 字节，尾部数据损坏，PPL 从 6.8 飙到 60** | 用普通模式（不加 `/J`）；复制后**必须抽样比对首尾哈希** |
| `iq_pack.py` 用普通 python | `ModuleNotFoundError: numpy` | 用引擎自带的 python（`data/terminal/current/python`） |
| `iq_pack.py` 不加 `--compat-bf16` | `output_hc_up.weight is Q8_0, but the engine requires BF16`，187 处 | 加 `--compat-bf16` |
| 长任务放在有时限的等待循环里 | 进程被静默回收，日志停在半句，无任何报错 | 等待循环**不设截止时间**；或让子进程脱离父进程 |
| 后台任务里 `-RedirectStandardOutput` 同名 | 两个进程抢同一日志，先写的被截断 | 每个实验用独立日志名 |
| `--tensor-type-file` 里混进非 `name=TYPE` 的行 | `parse_tensor_type: malformed tensor type 'python.exe'` | 写文件前用正则 `^[\w.]+=[A-Za-z0-9_]+$` 过滤 |
| 类型表只改了路由专家、忘了共享专家 | 以为在"精确复刻"，实际 `ffn_*_shexp` 还是 Q8_0 | 从原模型**逐张量**导出全部 1224 条，不要手工挑 |

## 追加：BF16 源实验（2026-11-16 晚）

假设「i-quant 必须从 BF16 量化」。下载了 329.72 GB 的 BF16 权重，用**原版逐个张量完全
相同的类型表**（`tools/` 脚本从原版导出的 1224 条，经 `type_diff.py` 校验 **0 处差异**）
量化了两次，唯一区别是 imatrix：

| 版本 | 源 | imatrix | 体积 | **PPL** | vs 原版 |
|---|---|---|---|---|---|
| 原版 UD-IQ4_XS | BF16 | Unsloth 官方 | 87.24 GB | **6.2488** | 基线 |
| A | BF16 | Unsloth 官方 | 87.24 GB | 7.1432 | +14.3% |
| B | BF16 | 游戏语料 | 87.24 GB | 7.0679 | +12.5% |

**假设被证伪**：从 Q8 换到 BF16 只回收 **1.3%**（7.2377 → 7.1432），不是预期的 15%。

### 但游戏 imatrix 第一次赢了

A 与 B 之间唯一的变量是 imatrix，**B 好 1.1%**。前七次实验要么源精度不对、要么类型
没对齐，这是第一次公平对照——**领域语料确实有效，只是幅度（1%）被工具链差异（13%）
完全淹没**。

### 真正的差异来源

把九次实验按「类型族」重排：

| 类型族 | 我们的最好成绩 | 原版 |
|---|---|---|
| **i-quant**（IQ2_S / IQ3_XXS / IQ4_XS / Q5_0） | 7.07 | **6.25** |
| **K-quant**（Q4_K） | **6.79** | — |

同一个源、同样的类型、同样的 imatrix，llama.cpp **b12407** 做不出 6.2488。

差异不在源精度、不在 imatrix、不在类型分配——**只剩量化器实现本身**。

### 可疑线索

llama.cpp 在 2026-10-28 合入 `Speed up IQ4 quant creation with pre-computed halfway
points (#31201)`。提速类改动若引入舍入差异，会让 i-quant 落到次优格点——**而 i-quant
恰恰对这类差异最敏感，K-quant 的 min/max 缩放则不受影响**。

这与观察到的现象吻合：i-quant 全线落后 13~18%，K-quant 只落后 8.7%。

**验证方法**（未执行，成本约 2 小时）：用 10-28 之前的 llama.cpp 构建重新量化一次，
看 i-quant 的 PPL 是否回落。若回落，说明是 b12407 的回归，可以向上游报告。

### 九次实验的结论

**用 llama.cpp 复现 Unsloth 的 UD-IQ4_XS 做不到，最好差 8.7%。**

- 想要**更好**：直接用 Unsloth 原版，或者等这个工具链问题查清
- 想要**更小**：K-quant + Q8 源，6.7897 / 91.96 GiB，比原版小 5%、差 9%，可控
- 想要**领域特化**：方向对（游戏 imatrix 赢 1.1%），但需要先解决工具链差异，否则
  1% 的收益看不见

## 追加：最后两个变量（2026-11-17 凌晨）

BF16 失败之后，还剩两个未验证的变量：工具版本，和类型表的钉法。

### 实验 11：换用 `#31201` 之前的 llama.cpp

`#31201`（"Speed up IQ4 quant creation with pre-computed halfway points"）合入于
2026-10-28 18:35 UTC。下载了它之前的最后一个构建 **b11960**，其余条件与实验 9 完全一致。

| 工具 | PPL |
|---|---|
| b12407（11-15） | 7.1432 |
| **b11960（10-28，改动之前）** | **7.1432** |

**小数点后四位完全相同。** `#31201` 不是质量回归；工具版本这两个点之间没有差异。

### 实验 12：最小干预（2 行类型表）

此前所有实验都用了完整的 `--tensor-type-file`。最小干预版本只保留两条——都是几何硬约束
（`ncols` 不能被 256 整除，K-quant 用不了），其余全部交给 llama.cpp 与官方 imatrix 决定：

```
ffn_down_exps.weight=IQ4_NL
per_layer_token_embd.weight=IQ4_NL
```

结果 **7.5002**，是所有 i-quant 尝试里最差的一次。

**这推翻了我"钉类型绕过了 llama.cpp 决策逻辑"的猜测——恰恰相反，精确复刻原版的类型分配
是所有 i-quant 尝试里最好的（7.14 vs 7.50）。类型表在帮忙。**

### 踩到的一个真崩溃

最小干预的第一次尝试用了 1 行类型表，直接崩溃：

```
per_layer_token_embd.weight  ncols=160, converting to iq4_xs
GGML_ASSERT(n_per_row%QK_K == 0) failed
```

`--token-embedding-type IQ4_XS` 会套用到这个 `ncols=160` 的张量，而 IQ4_XS 要求列数能被
256 整除。**这不是优雅回落，是断言崩溃。** 同一个张量如果在类型表里显式写了类型，反而会
走回落逻辑（打印 warning 后改用 IQ4_NL）。

**同一个输入，类型表里有没有那一行，决定了崩溃还是正常运行——这是 llama-quantize 的一
个真实缺陷**，比本文追的那 13% 更值得报给上游。

### 十二次实验的最终结论

| 维度 | 试过的取值 | PPL 跨度 |
|---|---|---|
| 源精度 | Q5_K_XL / Q8_0 / BF16 | 6.92 / 6.79~7.24 / 7.07~7.50 |
| imatrix | 无 / 游戏语料 / Unsloth 官方 | 6.79 / 7.07 / 7.14 |
| 类型表 | 2 行 / 1224 行精确复刻 / 自由 | 7.50 / 7.14 / 6.85 |
| 工具版本 | b11960 / b12407 | 7.1432 / 7.1432 |

**四个维度全部遍历。i-quant 的天花板是 7.07，原版是 6.25。**

Unsloth 的方法（逐层混合精度 + 高质量 imatrix）能对上的部分我们都对上了——
类型逐个张量零差异、官方 imatrix、BF16 源。仍然差 13%。

**结论：他们用的不是 llama.cpp 的 llama-quantize，或者用了私有补丁。**
他们的博客只说 v3.1 的 GGUF "可以在 llama.cpp 上运行"，从未说用它量化。

### 还剩的唯一方向

不是量化技巧，是**花更多位宽**：

| 目标 | 位宽 | 体积 | 预期 PPL |
|---|---|---|---|
| Q4_K_M（我们最好） | 4.58 BPW | 91.96 GiB | 6.7897 |
| Q5_K_M | 约 5.5 BPW | 约 110 GB | 待测，预计 6.2~6.5 |

位宽换质量是线性的，这条路确定能改善，代价是体积大 25%、解码更慢（专家从盘上流的量更多）。

## 最终定位：字节级比对（2026-11-18 凌晨）

前十五次实验都在比对**类型分配**，从没比对过**量化后的权重**。补上这一步之后，
问题第一次有了确定答案。

### 方法

直接比对两个 GGUF 的张量原始字节（不需要反量化，IQ3_XXS / Q5_0 / Q6_K 一视同仁）：

- 原版 `UD-IQ4_XS`（4 分片，87.24 GB）
- 我们的复刻版：BF16 源 + 从原版导出的 1224 条类型表 + **原版自己发布的 imatrix**

### 结果

```
原版 1224 个张量：
  ★ 730 个逐字节完全相同
  ★ 494 个不同
```

**不同的张量正好是"受 imatrix 影响"的那批**：

| 张量 | 类型 | 字节 |
|---|---|---|
| `token_embd.weight` | IQ4_XS | **相同**（322 MB） |
| `output.weight` | Q6_K | **相同**（497 MB） |
| `per_layer_token_embd.weight` | IQ4_NL | **相同**（28.8 GB，占模型 1/3） |
| `blk.*.ffn_gate_exps.weight` | IQ3_XXS | 不同（306 MB） |
| `blk.*.ffn_up_exps.weight` | IQ3_XXS | 不同（306 MB） |
| `blk.*.ffn_down_exps.weight` | Q5_0 | 不同（550 MB） |
| `blk.*.attn_qkv.weight` | Q6_K | 不同（21 MB） |
| `blk.*.hc_*` / `ssm_out` | Q8_0 | 不同 |

### 这组数据同时排除了三个悬着的问题

1. **源权重完全一致** —— 730 个张量字节级相同，说明输入数据一模一样
2. **量化器代码一致** —— 同样的输入和类型，非 imatrix 张量产出完全相同的字节
3. **类型分配正确** —— 导出的 1224 条表是对的

三个都证死了，剩下唯一的变量是 **imatrix 文件本身**。

### 结论

> **Unsloth 发布在仓库里的 `imatrix_unsloth.gguf`，不是量化这个 IQ4_XS 时实际使用的那份。**

模型元数据只记录文件名（`imatrix_unsloth.gguf`），不记录内容哈希。他们的校准集随时间更新
（文档提到 Calibration_v3 / v5），量化之后重新生成、覆盖同名文件是完全可能的。

**这解释了十五次实验为什么全部失败**：i-quant 的网格搜索完全依赖 imatrix 的数值，
用错的 imatrix 去逼近、无论怎么调源精度、位宽、工具版本，都追不回来。

### 与逐项实验的对应关系

| 改动 | 实测影响 | 与本文结论是否一致 |
|---|---|---|
| 源精度 Q5 → Q8 → BF16 | 1.3% | 一致（源本来就没问题） |
| 工具版本 b11960 → b12407 | 0.0% | 一致（工具没问题） |
| 位宽 4.23 → 5.26 BPW | 变差 0.25% | 一致（问题不在位宽） |
| 类型表 2 行 → 1224 行 | 0.7% | 一致（表是次要的） |
| imatrix 换成本地 512 窗口 | 0.9% | 一致（换的不是"对的那份"） |
| imatrix 换成本地 12288 窗口 | 0.5% | 一致（同上） |

### 还能做什么

**信息缺口，不是能力缺口。** 想要复现只能拿到那份未被覆盖的 imatrix；公开仓库里没有。

## 最后的测量：长上下文放大了全部差距（2026-11-18 清晨）

前十五次实验都用 `-c 512 --chunks 50` 评测。那不是这台机器的用法：实际工作是长上下文
agent 编程。用 `-c 32768` 重测后，结论比 512 口径严厉得多。

### 结果

| 上下文 | 原版 UD-IQ4_XS | 我们最好的 Q4_K_M | 差距 |
|---|---|---|---|
| **512** | 6.2488 | 6.7897 | **+8.7%** |
| **32768（2 chunks 累计）** | **10.1176** | **12.7255** | **+25.8%** |
| 32768（chunk 1 单独） | 18.0297 | 23.9519 | +32.8% |

原版跑满 6 chunks 的最终值是 6.3909；我们的模型内存放不下 32K 上下文（94.31 GB 模型
加 KV 超过 125 GiB），换页严重，2 个 chunk 用了 63 分钟，因此只测到 2 chunks。两个模型
在**同样的前 2 个 chunk** 上对比，口径一致。

### 为什么差距会放大

长上下文放大了注意力层的量化误差。512 窗口下注意力只覆盖局部，误差被平均掉；32K 下同一
个误差累积到每个 token 都要用的长程注意力上，逐层放大。

### 一个被验证的测量前提

同时做了一个对照：用 `llama-gguf-split --merge` 把原版的 4 个分片**原样合并**成单文件
（张量字节完全不变），再测 PPL：

```
原版 4 分片:                 6.2488 ± 0.15831
合并成单文件（字节未变）:    6.2488 ± 0.15831
```

**一位不差。** 这证明分片不影响 llama.cpp 的推理结果，也证明测量方法本身没有系统性偏差——
所以 7.1432 与 6.2488 的差异是真实的权重差异，不是测量假象。

### 这件事的最终结论

**用 llama.cpp 复现 Unsloth 的 UD-IQ4_XS 做不到，而且在真实的 32K 上下文下差距是 26%，
不是 512 口径下看起来的 8.7%。**

对这台机器的用途（长上下文 agent 编程）来说，原版是唯一选择，没有任何自制量化可以替代。
