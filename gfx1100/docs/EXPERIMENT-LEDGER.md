## 2. 逐 chunk 配对检验（**关键方法论**）

llama-perplexity 报的 `±0.18` 是 **chunk 间方差**，不是配对差值的误差。
三次实验同语料同 chunk，可以逐 chunk 配对：

| 对比 | 平均差 | SE | t | p | 判定 |
|---|---|---|---|---|---|
| up5 vs base | +0.2065 | 0.0298 | +6.93 | <0.001 | **显著** |
| down5 vs base | +0.1254 | 0.0125 | +10.04 | <0.001 | **显著** |

**配对后误差棒缩小 6~15 倍。**
**以后所有量化 A/B 必须逐 chunk 配对，不能看报告的总误差棒。**

## 3. 字节级比对（最硬的证据）

把我们的复刻版和原版逐张量比对**原始字节**：

```
原版 1224 个张量：
  730 个与我们的复刻版逐字节完全相同
  494 个不同
```

**相同的**：`token_embd`、`output`、`per_layer_token_embd`（28.8 GB）、所有 norm
**不同的**：`ffn_gate_exps`、`ffn_up_exps`、`ffn_down_exps`、`attn_qkv`、`hc_*`、`ssm_out`

**规律：不同的全部是"量化时查询 imatrix"的张量。**

再加上逐层误差测量：

```
同为 IQ4_NL 的 13 层：  我们 8.042%  vs  他们 8.025%   ← 量化器质量相同
他们的 Q5_0 层：        4.3%                          ← 误差减半（位宽更高）
```

**三条结论：**
1. **源权重相同**（730 个张量字节一致）
2. **量化器能力相同**（同类型误差差 0.016 个百分点）
3. **差距 100% 来自类型分配和 imatrix 数值**

### 最终判断

> **Unsloth 发布在仓库里的 `imatrix_unsloth.gguf` 不是量化 UD-IQ4_XS 时实际使用的那份。**
> 模型元数据只记录文件名，不记录内容哈希。

## 6. 引擎调优实测

### `--ple-io ram`（PLE 表锁进内存）— 6 次测量

| 组 | prefill | decode | 首个 token |
|---|---|---|---|
| ram ×3 | 1109.47 / 1091.52 / 1108.38 | 39.02 / 42.07 / 44.52 | 6297 / 6373 / 6281 ms |
| direct ×3 | 1047.09 / 1047.57 / 1035.64 | 41.27 / 42.56 / 42.64 | 6652 / 6637 / 6712 ms |

```
ram 平均 1103.1  direct 平均 1043.4  →  +5.7%
两组完全不重叠（最慢的 ram 快过最快的 direct）
```

**代价**：28.8 GB 锁页内存，启动 +8~25 秒，专家页缓存 48.7 → 23.9 GiB。

### `STRATA_ARENA_PIN_GIB`

| 值 | 专家槽位 | VRAM |
|---|---|---|
| `56`（写死） | 5826 | 13.31 GiB |
| `auto` | **5930~6120** | 13.53~13.97 GiB |

`auto` 用 `RAM/2 − 8 GiB ≈ 54.8 GiB`，比硬编码更贴合，且可移植（94 GiB 机器上约 39 GiB）。

### `STRATA_PF_FUSED`

PR #999 实测 gfx1100 上 **parity within noise** → 已从配置移除。

### `STRATA_PLE_BATCH=0`（正确性修复）

```
24 次冷启动:  默认 3/24 次静默读错提示词   设 0 后 0/24
代价: 3.5K 上下文 prefill 810 → 710 tok/s，decode 不变
```

**关键**：`verify.cpp` 返回 `!e || e[0] != '0'`，**不设置 = 开启**。

## 8. GLM-5.3-Flash 相关（另一条线）

### 官方只有 FP8

```json
"quantization_config": { "quant_method": "fp8", "weight_block_size": [128,128] }
```

**没有 BF16 版本。所有 GLM 量化都是从 FP8 出发的。**

```
45 层 × 288 专家 × (4096×2048×3) ≈ 326B 参数
FP8 305.8 GB  →  CPU/内存受限
每 token 激活 8 个专家（不是 10）
```

### 现有 3.0BIT 量化的实测

```
文件: D:\Strata-data-v31\models\GLM-5.3-Flash-3.0BIT\...q4kattn.gguf
大小: 113,585,695,168 字节
结构校验: 张量数据末端 == 文件大小（0 字节差）→ 没有截断
专家: Q2_K × 108 个（85.6 GB，全部统一）  注意力: Q4_K
```

**跑分（用户自己的 5 题评测）：**

| 臂 | 关思考 | 开思考 |
|---|---|---|
| Qwen IQ4_XS 精确 | 48.95 | — |
| **GLM 3.0BIT** | **23.40（崩盘）** | **48.41** |
| GLM UD-IQ2_XXS（Unsloth 2-bit） | **45.65** | 未测 |
| Qwen IQ3_S | 47.65 | — |
| IQ4@prior0.3 | 47.15 | — |

### **关键异常：2-bit 打赢 3-bit（关思考）**

```
UD-IQ2_XXS (2-bit):  45.65
3.0BIT     (3-bit):  23.40    ← 同为 reasoning_effort=none
```

**同样的参数、同样的模型，2-bit 干净而 3-bit 崩盘。**
且 ISTA-DASLab **没有发布过 GM 模型** → 这个 3.0BIT 是第三方手艺，质量无保障。
**文件结构完整，所以是量化质量差，不是下载损坏。**

### 鹈鹕 SVG 测试（用户自己评的）

| 模型 | 分数 | 实际画的是什么 |
|---|---|---|
| **GLM 3.0BIT（开思考）** | **9.0** | **真鹈鹕**（有喉囊）+ 头盔 + 太阳 + 链条牙盘 + 脚在踏板上 |
| Qwen IQ4_XS ×2 | 8.0 | 鹅/鸭（小尖嘴）、鸟浮在车架上、无踏板链条 |
| Qwen IQ3_S | 8.5 | 鹅/鸭，同上 |
| DeepSeek V4.1 IQ2_XS | 9.0 | **鸭**，车是歪的，鸟浮在车上方 |

**用户判断正确：只有 GLM 画出了鹈鹕的喉囊和场景元素。DeepSeek 那个 9.0 给高了。**
**评分标准要加严**：物种对不对（喉囊）+ 接触关系（坐在座垫、脚踩踏板）。旧标准只看"元素齐不齐"会漏掉致命错误。

### 专家使用分布（`PolyStrata-data\packs\glm-3.0bit\expert-profile.txt`）

```
12384 个 (层,专家) 对，43 层 × 288 专家，8822 万次路由

保留前 10% → 覆盖 28.9%     前 30% → 54.3%
保留前 50% → 72.6%          前 80% → 92.5%

每层内部保留一半 → 平均覆盖 72.0%（最低 63.6%）
```

**砍专家的代价太大，而且不会加速**（缓存里本来就是热专家）。

### GLM 速度瓶颈（已定位）

```
显存预算 23.2 GiB
  专家 13.2 GiB → 只有 1,700 / 12,384 个（13.8%）在显存
  KV   ~9.5 GiB（--kv-whole + 65536 上下文）

每 token 流式: 43 层 × 8 专家 × 6.9 MB ≈ 2.8 GB
→ 解码 19~20 tok/s 是货真价实的带宽瓶颈
```

**可做**：`--kv q8_0`（KV 减半，腾 ~4.75 GiB 给专家，预计 +8~12%），**不要用 `--kv-resident`**（长上下文反而变慢 + 锁 9.5 GB 内存）。

## 12. 一条最重要的教训

**16 次实验，每次都在"猜"类型分配，全部失败。**
真正解决问题的方法（GSQ-RCO）是**用梯度直接优化任务损失**，不是人工猜。
**在算力不够跑那个方法的前提下，6.6919 就是天花板。**

**所有未来的量化 A/B 必须：**
1. 逐 chunk 配对检验（不是看 ± 误差棒）
2. 在 32K 上下文下验证（512 口径会低估差距 3 倍）
3. 定性检查用鹈鹕 SVG（5 道 Python 题已经饱和，区分不出差异）
